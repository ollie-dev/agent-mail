# Windows milestone: Credential Manager store, Windows release and PowerShell installer

## Goal
agent-mail runs on Windows x64 for honest Agents. The human installs it with a PowerShell one-liner that checks the download's checksum, creates a Mandate in their own terminal (the Mandate goes into Windows Credential Manager) and gives the Agent Token to an Agent, which can then call `list` and every other agent command as on macOS. The README says plainly that on Windows any program running as the same user, including a hijacked Agent, can read stored Credentials (ADR-0002).

## Context
- Stack: Rust, one binary crate `agent-mail` (ADR-0001). Test: `cargo test`. Lint: `cargo clippy -- -D warnings` and `cargo fmt --check`. Windows target: `x86_64-pc-windows-msvc`.
- Ticket: `.scratch/agent-mail-v1/issues/18-windows.md` (blocked by 03 and 16, both merged). Background: `.scratch/agent-mail-v1/spec.md` (milestone 2), `GLOSSARY.md`, ADR-0002 (no service, so Windows protects only against honest Agents), ADR-0003 (add-only, immutable Mandates).
- State of `main` on Windows today (checked by running `cargo test --locked` on Windows 11 for this spec):
  - `RuntimeStore` is `EmptyStore` off macOS (`src/store.rs`), so `mandate create` fails with `store_unavailable` and every token is unknown.
  - `src/audit.rs` `home_from_user_database` returns `None` off Unix, so every audited command fails with `audit_unavailable`.
  - `src/terminal.rs` writes prompts' messages and the Agent Token to `/dev/tty` (`TTY_PATH`) and `InquireTerminal`'s TTY check opens it, so `mandate create` refuses to run on Windows.
  - `tests/release.rs` (`std::os::unix::fs::PermissionsExt`) and `tests/export.rs` line 793 (`std::os::unix::fs::symlink`) do not compile on Windows.
  - The repo has no `.gitattributes` and Windows checkouts get CRLF line endings (`core.autocrlf=true`, also the GitHub Windows runner default). That breaks every test that searches Markdown for `"\n## Heading\n"` or splits sources on `"\n"`: `tests/plugin.rs` (13 tests), `tests/project.rs`, `tests/search.rs` (2), `tests/mcp.rs` `ac8_…`, `tests/audit.rs` `ac7_…`, `tests/create.rs` `ac11_…`, `tests/gmail_live.rs` `live_round_trip_is_ignored_by_default`.
  - `src/audit.rs` unit test `other_unix_path_follows_xdg_data_home` fails because `/x/data` is not an absolute path on Windows.
  - `src/selfcheck.rs` already passes off macOS (`evaluate` returns `true` unless `cfg(all(target_os = "macos", not(debug_assertions)))`).
- Files this feature touches:
  - `Cargo.toml` (`[target.'cfg(windows)'.dependencies]`, e.g. `windows-sys` with `Win32_Foundation`, `Win32_Security_Credentials`, `Win32_UI_Shell`, `Win32_System_Com`; `keyring` cannot enumerate items, which `mandate list` needs), `Cargo.lock`.
  - `src/store.rs`: new `CredentialManagerStore` (cfg(windows)) and `RuntimeStore = CredentialManagerStore` on Windows; `EmptyStore` stays for other non-macOS targets.
  - `src/audit.rs`: Windows log location.
  - `src/terminal.rs`: the controlling-terminal path on Windows (`CONOUT$`).
  - `.gitattributes` (new): `* text=auto eol=lf`.
  - `tests/release.rs`, `tests/export.rs`, `src/audit.rs` tests: gate Unix-only parts with `#[cfg(unix)]`.
  - New `tests/credential_manager.rs` (opt-in, ignored by default, `#![cfg(windows)]`).
  - New `install.ps1` at the repo root; `.github/workflows/release.yml`; new `.github/workflows/ci.yml`; `scripts/verify-release.sh`; `.github/release-notes.md`; `README.md`; `CLAUDE.md` (list the new files and tests).

## Acceptance criteria
Each criterion keeps the ticket's wording; the lettered points are the concrete checks, one test each.

1. AC1: On Windows, `mandate create` stores the Mandate in Credential Manager and `list` with the printed token works (opt-in test, ignored by default).
   - a. `tests/credential_manager.rs`, `#![cfg(windows)]`, one test marked `#[ignore = "writes to the real Windows Credential Manager; run with `cargo test --test credential_manager -- --ignored`"]`. It runs `mandate create` in-process with the scripted terminal (one generic Account on the fake IMAP server, Grant `list` on `INBOX`) against `CredentialManagerStore` and a temporary audit log, takes the Agent Token the scripted terminal was shown, then runs `list` through the core with that token and the same store: the result names `INBOX`. It then deletes the Mandate with `mandate delete <id>` and asserts `list` with the same token fails with the unknown-token error. Without `--ignored`, `cargo test` on Windows reports it as ignored.
   - b. In the same opt-in file: `CredentialManagerStore` `put` of a key and a 6,000-byte value, then `get` returns exactly those bytes; a second `put` under the same key fails and `get` still returns the first value (add-only, ADR-0003); `entries()` lists that key exactly once; `delete` returns `Ok(true)`, then `get` returns `Ok(None)` and `delete` returns `Ok(false)`. No Credential Manager item whose target name starts with `agent-mail:` and contains that key is left (checked through `CredEnumerateW` with filter `agent-mail:*`).
   - c. Storage layout, testable in-process as pure functions on every OS: one generic credential per Mandate, target name `agent-mail:` followed by the base64url (no padding) store key, persisted `CRED_PERSIST_LOCAL_MACHINE`. A value longer than the Credential Manager blob limit (2,560 bytes) is split into parts of at most 2,560 bytes: the first part under `agent-mail:<key>`, later parts under `agent-mail:<key>#1`, `agent-mail:<key>#2`, …; the first part records the number of parts. Split then join of values of length 0, 1, 2,560, 2,561 and 6,000 returns the original bytes; a 6,000-byte value gives 3 target names in that order; a join with a missing part fails (`StoreError::Unavailable`). An item under `agent-mail:` whose name does not decode is counted in `entries()` with an empty value, never targeted, as `KeychainStore` does.
   - d. Audit log location on Windows: `log_path(Platform::Windows, Path::new(r"C:\Users\alice\AppData\Local"), None)` returns `C:\Users\alice\AppData\Local\agent-mail\audit.log` (the base is the Local AppData known folder, `SHGetKnownFolderPath(FOLDERID_LocalAppData)`, not an environment variable). A test on Windows asserts `audit::platform_path()` is `Some` and ends with `agent-mail\audit.log`.
   - e. On Windows the controlling terminal for messages and the Agent Token is `CONOUT$`, not `/dev/tty`. A source test asserts `src/terminal.rs` uses `CONOUT$` under `cfg(windows)` and `/dev/tty` under `cfg(unix)`, and `write_tty` still never touches stdout or stderr (the existing `ac11_real_terminal_writes_the_token_to_dev_tty_only` keeps passing on both OSs).
2. AC2: The hardened-runtime self-check is macOS-only and does not block Windows.
   - a. On Windows (test gated `#[cfg(windows)]` in `tests/selfcheck.rs`): `agent_mail::selfcheck::check()` returns `true`, and `GuardedStore::new(InMemoryStore::new())` `put` then `get` of a key and value succeeds and returns the value.
   - b. On every OS: a source test asserts the only active `evaluate` in `src/selfcheck.rs` is under `cfg(all(target_os = "macos", not(debug_assertions)))` and the fallback under `cfg(not(all(target_os = "macos", not(debug_assertions))))` returns `true`, and that `src/main.rs` wraps `RuntimeStore` in `GuardedStore::new` on all OSs (so Windows builds also go through the guard, which passes).
   - c. The README's Install section says the hardened-runtime check and `hardened_runtime_missing` apply to macOS only.
3. AC3: A release tag produces a Windows x64 binary on GitHub Releases with a SHA-256 checksum and a build attestation.
   - a. `.github/workflows/release.yml` has a job `build-windows` with `runs-on: windows-latest`, `needs: test`, permissions `contents: read` only, that runs `cargo build --release --locked --target x86_64-pc-windows-msvc`, packages `agent-mail.exe` alone into `agent-mail-x86_64-pc-windows-msvc.zip`, writes `agent-mail-x86_64-pc-windows-msvc.zip.sha256` in `shasum -a 256` format (64 lowercase hex digits, two spaces, the asset name, LF), and uploads both as a workflow artifact.
   - b. `publish` has `needs: [test, build-windows]`, downloads that artifact into `dist/`, lists `dist/agent-mail-x86_64-pc-windows-msvc.zip` in the `attest-build-provenance` `subject-path` next to the two macOS tarballs, and passes the zip, its `.sha256` and `dist/install.ps1` (copied from the repo root) to `gh release create`. Every `uses:` in the workflow is pinned to a full commit SHA with a version comment, as today.
   - c. `scripts/verify-release.sh <tag>` also downloads the Windows zip and its `.sha256`, checks the `.sha256` format and the checksum, checks the zip holds exactly `agent-mail.exe`, and runs `gh attestation verify` on it (no signature check, no run). A test asserts the script names `agent-mail-x86_64-pc-windows-msvc.zip` and still parses with `sh -n` (Unix only).
   - d. The `test` job runs on a matrix `os: [macos-latest, windows-latest]` with `contents: read`, so a Windows test failure blocks `publish`.
4. AC4: The PowerShell installer downloads the binary, verifies the checksum, aborts on a mismatch, and installs to the user's local bin directory.
   - Tests in `tests/release.rs` under `#[cfg(windows)]` run `powershell.exe -NoProfile -ExecutionPolicy Bypass -File install.ps1` with `USERPROFILE` set to a fresh temporary directory and `AGENT_MAIL_DOWNLOAD_URL` set to a `file:///` URL of a temporary download directory holding a test zip (built in the test with `Compress-Archive`, holding a small `agent-mail.exe`) and its `.sha256`. The installer must run under Windows PowerShell 5.1 and PowerShell 7.
   - a. Matching checksum: exit code 0, `%USERPROFILE%\.local\bin\agent-mail.exe` exists with the zip's `agent-mail.exe` bytes, stdout names that path, and the installer's temporary directory is gone.
   - b. An existing `%USERPROFILE%\.local\bin\agent-mail.exe` is replaced.
   - c. Checksum mismatch (the `.sha256` holds a different valid digest): non-zero exit, stderr contains `checksum mismatch for agent-mail-x86_64-pc-windows-msvc.zip; nothing was installed`, and `%USERPROFILE%\.local\bin` holds no `agent-mail.exe` (and no staging file).
   - d. Malformed `.sha256` (not `^[0-9a-f]{64}  agent-mail-x86_64-pc-windows-msvc.zip$`): non-zero exit, stderr says the checksum file is malformed and nothing was installed; nothing installed.
   - e. Missing zip in the download directory: non-zero exit, nothing installed.
   - f. A zip holding a file other than `agent-mail.exe` only: non-zero exit, nothing installed.
   - g. Source checks on every OS: `install.ps1` never contains `Start-Process` with `-Verb RunAs`, never runs the downloaded binary, does not change `PATH` itself (when `%USERPROFILE%\.local\bin` is not on `PATH` it only prints a hint), and refuses with a message naming x64 when `PROCESSOR_ARCHITECTURE` is not `AMD64`.
5. AC5: The README's Windows section states that a hijacked Agent can read Credentials on Windows.
   - a. Under `## What each OS protects against`, the `**Windows.**` paragraph says Credentials live in Windows Credential Manager, any program running as the same user can read them, a hijacked Agent can read (extract) the Credentials, so the Windows build protects only against honest Agents. It no longer says there is no Windows release. A test asserts the paragraph contains `Credential Manager`, `hijacked Agent`, `same user` and `honest Agents`, and not `no Windows release`.
   - b. `## Install` gives the Windows one-liner `irm https://github.com/ollie-dev/agent-mail/releases/latest/download/install.ps1 | iex`, says it installs to `%USERPROFILE%\.local\bin\agent-mail.exe` after verifying the SHA-256 checksum, and shows `gh attestation verify agent-mail-x86_64-pc-windows-msvc.zip --repo ollie-dev/agent-mail`. `## Audit log` lists `Windows: %LOCALAPPDATA%\agent-mail\audit.log`. `.github/release-notes.md` holds the Windows one-liner. Tests assert these strings.
6. AC6: All tests that do not need a platform store pass on Windows CI.
   - a. New `.github/workflows/ci.yml` runs on `push` to `main` and on `pull_request`, permissions `contents: read`, matrix `os: [macos-latest, windows-latest]`, step `cargo test --locked`; actions pinned to full SHAs. A test asserts these.
   - b. `.gitattributes` exists with `* text=auto eol=lf`, so the tests listed in Context that search for `"\n"` pass on a Windows checkout.
   - c. `tests/release.rs` and `tests/export.rs` compile on Windows (Unix-only checks gated `#[cfg(unix)]`), and `other_unix_path_follows_xdg_data_home` is gated or uses a platform-absolute path, so `cargo test --locked` on Windows ends with zero failures and only the opt-in tests ignored.
   - d. `cargo clippy --all-targets -- -D warnings` passes on Windows and macOS (no unused imports or dead code under either cfg).

## Out of scope
- Protection against a hijacked Agent on Windows (ADR-0002); Windows Hello confirmation.
- Windows arm64 builds, code signing (Authenticode), winget/Scoop packages.
- Linux release builds and a libsecret store (v2).
- A Windows equivalent of the release-binary tests in `tests/selfcheck.rs`, and running the release binary in `verify-release.sh`.
- Restricting the Windows audit log file with ACLs (the macOS/Unix mode rules stay Unix-only; the README says any process running as the user can read it anyway).
- Changing the Claude Code plugin; `.mcp.json`'s `agent-mail` command already resolves `agent-mail.exe` on `PATH`.

## Notes for reviewers
- Security: the new store holds sealed Mandates (Credentials inside), but on Windows DPAPI lets any same-user process decrypt them; this is the accepted honest-Agent-only model and the README must say so without hedging. Check: `put` stays add-only (read before `CredWriteW`; never overwrite or update an existing item, including any part), nothing logs or prints a store value, target names hold only the token-derived key, `RuntimeStore` is fixed at compile time with no runtime selection, the in-memory store stays behind `cfg(any(test, feature = "test-support"))`, and the Windows release build still compiles without `test-support`. `install.ps1` handles untrusted downloads: checksum file format checked before use, nothing extracted before the checksum passes, only `agent-mail.exe` taken, no elevation, nothing executed. The checksum only catches corruption or tampering in transit, not a compromised release; attestation covers provenance. Workflow: `build-windows` has read-only permissions; only `publish` holds `contents: write`, `id-token: write`, `attestations: write`.
- Split records: the ticket says nothing about the 2,560-byte Credential Manager blob limit, but a sealed Mandate (JSON listing plus JSON plaintext, see `src/seal.rs`) with several Accounts or many mailboxes can exceed it, so AC1c adds splitting. If reviewers prefer a size cap instead, it must fail with `store_unavailable` before writing anything.
- Testability: AC1a and AC1b need a real Windows Credential Manager and are opt-in only; AC1c, AC1d and AC1e cover the logic in default runs. AC6 can only be fully proven on a Windows runner; the builder should run `cargo test --locked` on Windows locally if available.
- UX: the human (operator) runs the PowerShell installer and `agent-mail mandate create` in their own Windows Terminal or console; Agents call the CLI or `agent-mail mcp` as on macOS. Messages stay short, one thing each, matching `install.sh`'s wording.
- UI: terminal output only: installer progress and error lines, the `mandate create` prompts on the Windows console, and README text. No pages.
