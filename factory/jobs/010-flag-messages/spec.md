# Set and clear the read and starred flags

## Goal
An Agent runs `agent-mail flag <REF> --set seen` (or `--clear seen`, `--set flagged`, `--clear flagged`) with a message reference from `search` to mark a message read or unread, or starred or unstarred, and gets back the message's flags after the change. Only `\Seen` and `\Flagged` can be changed in v1. Any other flag is rejected with a structured `unsupported_flag` error. The call needs a `flag` Grant on the reference's Account and mailbox. A stale reference changes nothing. Every call appends an audit entry with the message reference and the flag change.

A new `stores()` accessor returns each store's argument string, e.g. `1 +FLAGS (\Seen)`. Existing tests that assert no `STORE` keep passing.

### Command line
`agent-mail flag <REF> (--set <FLAG> | --clear <FLAG>)`, plus `--text` (global or after the subcommand).
- `<REF>`: a message reference as `search` prints it, parsed with `read::parse_reference`. A reference that does not parse is a usage error: exit 2, no connection, no audit entry.
- Exactly one of `--set` or `--clear` must be given. Neither, both, or one given twice is a usage error from clap (exit 2, no audit entry).
- `<FLAG>` is accepted by clap as any string. The core accepts, ASCII case-insensitively, only `seen` or `\Seen` (the message is read) and `flagged` or `\Flagged` (the message is starred). Anything else fails with `unsupported_flag` (AC3). Only the canonical `\Seen` or `\Flagged` is ever sent to the server, never the Agent's text.
- The Account is the Mandate's Account whose login equals the reference's account, as for `read`.

### Result (JSON, one line on stdout)
```json
{"ref":"agent@example.test/Triage/1700000007/1","account":"agent@example.test","mailbox":"Triage","flags":["\\Seen"]}
```
Keys exactly these, in this order. `flags` holds every flag of the message after the change, as the server reports them, in server order. Setting a flag that is already set, or clearing one that is not, succeeds and reports the unchanged flags.

### Fake server fixture (used by the criteria below)
A new mailbox `Triage`, UIDVALIDITY `1700000007`, not added to `SERVER_MAILBOXES`. It holds two simple messages (`source: None`):

| UID | From | Subject | Flags |
|---|---|---|---|
| 1 | `alice@example.com` | `Triage one` | none |
| 2 | `bob@example.com` | `Triage two` | `\Seen \Flagged \Answered` |

Unless a criterion says otherwise, tests use the Mandate `aaaa1111` with the single Account `agent@example.test` (`support::LOGIN`) and Grants `flag` on `Triage` and `search` on `*`. References are written `T(n)` = `agent@example.test/Triage/1700000007/<n>`. "Flags of T(n)" means the fake's `all_flags()` entry for `Triage` UID n after the call.

## Acceptance criteria
1. AC1: Marking a message read sets `\Seen` on the fake server; marking it unread clears it. Test: `flag T(1) --set seen` exits 0 and stdout is exactly `{"ref":"agent@example.test/Triage/1700000007/1","account":"agent@example.test","mailbox":"Triage","flags":["\\Seen"]}`. The flags of T(1) are `[\Seen]` and those of T(2) are unchanged. The fake's `commands()` contain `SELECT` and `UID STORE`. They contain no `CLOSE`, `EXPUNGE` or `UID EXPUNGE`, and no fetch item other than `UID` and `FLAGS` was requested. Then `flag T(1) --clear seen` exits 0 with `"flags":[]`, and the flags of T(1) are `[]`. `flag T(2) --clear '\SEEN'` gives `"flags":["\\Flagged","\\Answered"]`, so the backslash form and case-insensitive matching work and `\Answered` is kept. `flag T(1) --clear seen` on an already unread message exits 0 with `"flags":[]`. `--text` prints one line `agent@example.test/Triage/1700000007/1: \Seen`, or `...: no flags` when `flags` is empty.
2. AC2: Starring sets `\Flagged`; unstarring clears it. Test: `flag T(1) --set flagged` exits 0 with `"flags":["\\Flagged"]`, and the flags of T(1) are `[\Flagged]`. Then `flag T(1) --clear flagged` exits 0 with `"flags":[]`, and the flags of T(1) are `[]`. `flag T(2) --clear '\Flagged'` gives `"flags":["\\Seen","\\Answered"]`. The fake's `stores()` hold `1 +FLAGS (\Flagged)` and `1 -FLAGS (\Flagged)`, optionally with `.SILENT` after `FLAGS`.
3. AC3: Any other flag is rejected with a structured error. Test: for each of `--set deleted`, `--set '\Deleted'`, `--clear '\Answered'`, `--set '$Junk'`, `--set '\Draft'`, `--set ''` and `--set $'seen\r\n'`, run against T(1). Each exits 1, stdout is empty, and stderr parses as `{"error":{"code":"unsupported_flag","operation":"flag","message":...}}` with no other keys. The message names `seen` and `flagged` as the only flags that can be changed. It does not echo the rejected value. The fake sees no connection, and the flags of T(1) and T(2) are unchanged. `--text` prints `error: unsupported_flag: ...`. The existing `every_error_message_names_a_next_step` test covers the new variant. Usage errors: `flag T(1)` (no action) and `flag T(1) --set seen --clear flagged` each exit 2 with nothing on stdout.
4. AC4: Flagging in a mailbox without a `flag` Grant is denied and audited. Test, each case against a fresh audit log: (a) Grants `read` and `search` on `Triage` and `flag` on `INBOX`, then `flag T(1) --set seen`; (b) an empty Policy, then `flag T(1) --set seen`; (c) the default Grants, then `flag other@example.test/Triage/1700000007/1 --set seen` (an Account the Mandate does not cover). Each exits 1, stdout is empty, and stderr parses as `{"error":{"code":"denied","operation":"flag","account":<the reference's account>,"mailbox":"Triage","message":...}}`. The fake server sees no connection, and the flags of T(1) are unchanged. The log holds one line `{"time":T,"mandate":"aaaa1111","operation":"flag","account":<the reference's account>,"mailbox":"Triage","messages":[<the reference>],"change":"+\\Seen","outcome":"denied","reason":"denied"}`.
5. AC5: A stale message reference fails without changing any flag. Test: `flag agent@example.test/Triage/1700000099/1 --set seen` exits 1, stdout is empty, and stderr parses as `{"error":{"code":"stale_reference","operation":"flag","account":"agent@example.test","mailbox":"Triage","message":...}}`. The message says no flag was changed and tells the Agent to search the mailbox again for a fresh reference. The fake sees `SELECT` but no `UID FETCH` and no `UID STORE`, and every `Triage` message's flags are unchanged. `read` with a stale reference still reports `"operation":"read"`. A reference to a missing UID (`agent@example.test/Triage/1700000007/99 --set seen`) fails with `message_not_found`, `"operation":"flag"`, and no `UID STORE`.
6. AC6: Each change appends an audit entry with the message reference and the flag change. Test: `flag T(1) --set seen` appends exactly one line `{"time":T,"mandate":"aaaa1111","operation":"flag","account":"agent@example.test","mailbox":"Triage","messages":["agent@example.test/Triage/1700000007/1"],"change":"+\\Seen","outcome":"allowed"}`, keys in this order, with no `results` key. `--clear flagged` logs `"change":"-\\Flagged"`. AC5's stale call logs `"change":"+\\Seen","outcome":"allowed","reason":"stale_reference"`, and the missing-UID call logs `"reason":"message_not_found"`. An AC3 rejection logs one line with `"messages":[<ref>]`, no `change` key, `"outcome":"denied","reason":"unsupported_flag"`, and its bytes never contain the rejected value (`$Junk`). A malformed reference (`flag not-a-ref --set seen`) exits 2 and logs nothing. After AC1 and AC2's calls, the log bytes never contain a subject (`Triage one`), an address from a message (`alice@example.com`), the Credential, the Agent Token or its token hash. `list`, `search` and `read` entries never carry a `change` key.

## Out of scope
- Flags other than `\Seen` and `\Flagged`: `\Answered`, `\Deleted`, `\Draft`, keywords such as `$Junk`, and Gmail labels (`X-GM-LABELS`).
- Several changes or several messages in one call, UID ranges, and flagging by search criteria.
- Replacing the whole flag set (`FLAGS` without `+`/`-`) from the CLI. The fake supports it only for completeness.
- `CONDSTORE`/`UNCHANGEDSINCE` conditional stores.
- `--account` and several tokens (ticket 13), the MCP `flag` tool (ticket 15), and the live Gmail test (ticket 12).
- Moving messages (ticket 10).

## Notes for reviewers
- Security:
  - This is the first command that changes mailbox state through the Credential. The Policy check (`flag` on the reference's Account and decoded mailbox) must happen before any connection (AC4 asserts no connection). The Account is matched by exact login, so a reference naming an uncovered Account never uses another Account's Credential.
  - The flag name is untrusted Agent input. It is never sent to the server. The core maps it to one of two fixed literals, `\Seen` or `\Flagged`, and rejects everything else before connecting (AC3). This rules out IMAP injection through the flag argument, including CR/LF. The rejected value is neither echoed in the error nor written to the audit log, so no Agent-chosen text reaches either. The reference gets the same checks as in `read` (`is_valid_reference`, applied again in the core, because the MCP adapter will call the core directly).
  - `SELECT` is needed for `STORE`, so the mailbox is opened read-write. The connector must never send `CLOSE`, which silently expunges messages the human already marked `\Deleted`. It must also never send `EXPUNGE` or fetch a body, since a non-peek fetch would set `\Seen` as a side effect. AC1 asserts this. The session ends with `LOGOUT` only.
  - The UIDVALIDITY check comes after `SELECT` and before any `UID FETCH` or `UID STORE` (AC5), so a renumbered mailbox never has the wrong message changed. Checking existence before the store stops a missing UID from being reported as success.
  - The audit entry records the reference and the change (`+\Seen`, `-\Flagged`), never subjects or addresses (AC6). A denied or failed call still logs the attempted change. The `change` key, the `unsupported_flag` code, the `seen`/`flagged` names and the result shape are this spec's concrete choices, made so the ticket's criteria are testable. The ticket names none of them.
  - An unsupported flag is logged with `"outcome":"denied"`, because the call ends before the Policy grants anything. This matches how `read` logs `invalid_reference`.
- UX: The user is an Agent calling the CLI, usually through the skill. Typical flow: `agent-mail search --mailbox INBOX --unseen`, then `agent-mail read <ref>`, then `agent-mail flag <ref> --set seen` once it has handled the message, or `--set flagged` to star it for the human. The returned `flags` confirm the new state, and repeating a call is harmless. `seen`/`flagged` avoid shell-escaping a backslash, while `\Seen`/`\Flagged` as `search` prints them are also accepted. A denial names operation, Account and mailbox, so the Agent can tell the human which Grant to add. `--help` for `flag` explains the reference argument, the two accepted flags and their meaning (read, starred), and that exactly one of `--set`/`--clear` is required.
- UI: Terminal output only. JSON by default: one line on stdout as shown under "Result". Errors are JSON on stderr. With `--text`: one line `<ref>: <flags joined by spaces>`, or `<ref>: no flags`, with every value passed through `escape_controls`.
