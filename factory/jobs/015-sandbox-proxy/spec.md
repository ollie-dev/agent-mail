# Connect through the Claude Code sandbox proxy

## Goal
With the Claude Code sandbox on, there is no direct network: traffic has to go through the sandbox proxy, and the system certificate verifier is unavailable. After this ships, an Agent's `agent-mail` calls (`list`, `search`, `read`, `flag`, `move`, `draft`, and the live login check of `mandate create`) reach the IMAP server through the proxy named in `HTTPS_PROXY` or `ALL_PROXY` (HTTP CONNECT or SOCKS5, with proxy credentials taken from the URL) and verify TLS against built-in root certificates. With no proxy set, agent-mail keeps connecting directly with system verification.

## Context
- Stack: Rust, one binary crate `agent-mail` (ADR-0001). Test: `cargo test`. Lint: `cargo clippy -- -D warnings` and `cargo fmt --check`.
- Source ticket: `.scratch/agent-mail-v1/issues/14-sandbox-proxy.md`. Product spec: `.scratch/agent-mail-v1/spec.md`, section "Network and TLS" and "Proxy tests". The spec names `webpki-roots` for the built-in roots.
- Files this feature touches:
  - `Cargo.toml` / `Cargo.lock`: add `webpki-roots`. Write the CONNECT and SOCKS5 client handshakes by hand in a small module rather than pulling in a proxy crate, to keep the footprint small (the builder may choose a crate if it is small and has no runtime cost, and must say why).
  - `src/proxy.rs` (new): proxy URL parsing from the environment, the HTTP CONNECT and SOCKS5 handshakes, and the proxy error type.
  - `src/imap.rs`: `Network` gains an optional proxy; `login` opens its TCP stream through the proxy when one is set; `tls_connector` picks the built-in roots in proxy mode; new `ImapError` variants for a proxy refusal and an invalid proxy setting.
  - `src/core.rs`: the run builds the proxy from the `env` map passed to `agent_mail::run` (not from the process environment, so tests drive it in-process); new `CoreError` variants and codes `proxy_refused` and `invalid_proxy`; `ErrorBody` gains an optional `host` field.
  - `src/lib.rs` if needed for wiring; `src/create.rs` only if the live login check needs the env-derived network passed in.
  - `tests/proxy.rs` (new): integration tests; `tests/support/`: a minimal in-process CONNECT proxy and SOCKS5 proxy (real TCP on 127.0.0.1, records each requested target host and port and any credentials received, can be told to refuse a host).
  - `README.md`: a short "Sandbox and proxies" section with the behaviour and the two new error codes. `CLAUDE.md`: add `src/proxy.rs` and `tests/proxy.rs` to the layout list.
- Behaviour details (apply to every criterion):
  - Proxy selection, first non-empty wins: `HTTPS_PROXY`, `https_proxy`, `ALL_PROXY`, `all_proxy`. An empty value counts as unset. `HTTP_PROXY` and `NO_PROXY` are ignored.
  - The proxy URL's scheme picks the protocol: `http://` (or no scheme) is HTTP CONNECT, default port 80; `socks5://` and `socks5h://` are SOCKS5, default port 1080. Any other scheme (including `https://`), a missing host, a bad port or an unparsable URL is `invalid_proxy`.
  - The Account's host name is always sent to the proxy unresolved (CONNECT `host:port`; SOCKS5 address type DOMAINNAME), because the sandbox has no DNS of its own. agent-mail does not resolve it locally in proxy mode.
  - Credentials in the URL (`scheme://user:pass@host:port`, percent-decoded) are sent as `Proxy-Authorization: Basic base64(user:pass)` for CONNECT and as RFC 1929 username/password authentication for SOCKS5 (offering only method 0x02 when credentials are present, only 0x00 when not).
  - The CONNECT reply is read up to the end of its headers (`\r\n\r\n`, at most 8 KiB) without consuming bytes past it, so a server greeting that arrives right after the `200` (STARTTLS mode) is not lost.
  - TLS is unchanged on top of the tunnel: implicit TLS or mandatory STARTTLS, verifying the Account's own host name.
  - The test-only `TlsTrust::OnlyRoots` hook still wins over the built-in roots in proxy mode, so tests can reach the fake IMAP server through a proxy.
  - A proxy that cannot be reached, or that sends a malformed reply, is `connection_failed`, as for a direct connection.

## Acceptance criteria
1. AC1: With `HTTPS_PROXY` pointing at an in-process CONNECT proxy, `list` reaches the fake IMAP server through the proxy (the proxy observes the tunnel). Input: a Mandate with a `list` Grant on `INBOX` for the fake Account on `localhost:<fake port>` (implicit TLS), env `HTTPS_PROXY=http://127.0.0.1:<proxy port>`, `Context::trusting_only` with the fake CA. Expected: exit code 0, the same JSON mailbox list as the direct `list` test, and the proxy recorded exactly one `CONNECT localhost:<fake port>` tunnel. A second test does the same with the Account in STARTTLS mode and also succeeds.
2. AC2: With `ALL_PROXY` pointing at an in-process SOCKS5 proxy, the same works. Input: as AC1 but env `ALL_PROXY=socks5://127.0.0.1:<proxy port>` and no `HTTPS_PROXY`. Expected: exit code 0, the same mailbox list, and the SOCKS5 proxy recorded one CONNECT request with address type DOMAINNAME for `localhost` and port `<fake port>`. A further test sets both `HTTPS_PROXY` (CONNECT proxy) and `ALL_PROXY` (SOCKS5 proxy) and checks only the CONNECT proxy saw a tunnel.
3. AC3: Proxy credentials in the URL are sent to the proxy and never appear in output or the audit log. Input: `HTTPS_PROXY=http://proxyuser:pr%40xy-secret@127.0.0.1:<port>` against the CONNECT proxy, and `ALL_PROXY=socks5://proxyuser:pr%40xy-secret@127.0.0.1:<port>` against the SOCKS5 proxy, each with a test audit log. Expected: the CONNECT proxy received `Proxy-Authorization: Basic ` + base64 of `proxyuser:pr@xy-secret`, the SOCKS5 proxy received username `proxyuser` and password `pr@xy-secret` via RFC 1929, `list` succeeds, and neither `proxyuser`, `pr@xy-secret`, `pr%40xy-secret` nor the base64 string appears in stdout, stderr or any audit log line; the same holds when the proxy refuses (AC4's setup with credentials) and when the URL is invalid (e.g. `HTTPS_PROXY=ftp://proxyuser:pr%40xy-secret@127.0.0.1:1`, which fails with code `invalid_proxy` naming the variable `HTTPS_PROXY` but not echoing its value, with nothing connected to).
4. AC4: A proxy refusal (e.g. 403 for a host not on the allowlist) produces a structured error naming the host. Input: the CONNECT proxy answers `HTTP/1.1 403 Forbidden` for `localhost:<fake port>`; separately the SOCKS5 proxy answers reply code `0x02` (connection not allowed by ruleset). Expected for both: exit code 1, stderr JSON `{"error":{"code":"proxy_refused","account":"agent@example.test","host":"localhost",...}}` whose `message` names `localhost:<fake port>` and tells the Agent to ask the human to allow that host in the sandbox's allowed domains; the fake IMAP server saw no connection; the audit line has `outcome` `allowed` and `reason` `proxy_refused`.
5. AC5: Without proxy variables, connections are direct. Input: the CONNECT and SOCKS5 proxies are running, env holds only `AGENT_MAIL_TOKEN` (and, in a second case, `HTTPS_PROXY=` and `ALL_PROXY=` set to empty strings, plus `HTTP_PROXY` pointing at the CONNECT proxy). Expected: `list` succeeds with the fake server's mailboxes, the fake server saw one connection, and neither proxy recorded any connection.
6. AC6: In proxy mode, TLS verification uses the built-in roots, and a certificate not chained to a trusted root is rejected. Input (integration): a production-trust context (`Context::new(&store)` with a test audit log, so no `OnlyRoots` hook) with `HTTPS_PROXY` at the CONNECT proxy and the fake server whose certificate chains only to the test CA. Expected: exit code 1, error code `tls_certificate`, and the proxy recorded the tunnel (the failure is at verification, not at connect). Input (unit, in `src/imap.rs`): the TLS trust chosen for a `Network` with a proxy and default trust. Expected: it is the built-in roots variant, its root store holds `webpki_roots::TLS_SERVER_ROOTS.len()` anchors, and a `Network` without a proxy still selects the platform verifier.

## Out of scope
- The README section listing the Claude Code sandbox allowed-domain settings for mail hosts (ticket 17).
- `NO_PROXY` handling, `HTTP_PROXY`, TLS to the proxy itself (`https://` proxy URLs), SOCKS4, and proxy authentication schemes other than Basic and RFC 1929.
- Proxy support for anything other than IMAP connections (there is no other network traffic in v1 yet; the MCP server is ticket 15).
- Detecting the sandbox to switch verification; proxy mode alone decides it.
- Windows specifics (ticket 18) and a live test through the real Claude Code sandbox.

## Notes for reviewers
- Security: proxy URLs are untrusted input from the environment and may carry proxy credentials. They must never reach stdout, stderr, error messages, the audit log, or `Debug` output (`Network` currently derives `Debug`; the proxy field needs a redacting impl like `TlsTrust`'s), and must not be stored in fixtures beyond the obviously fake test values. The IMAP Credential still goes only over the TLS session established end-to-end through the tunnel; the proxy sees only ciphertext. Built-in roots replace the platform verifier only in proxy mode; the test-only `OnlyRoots` hook stays behind `cfg(any(test, feature = "test-support"))` and the release-build marker check must still pass. CONNECT reply parsing must be bounded (8 KiB) and SOCKS5 replies length-checked, since a hostile proxy controls those bytes. The Account host is sent to the proxy as-is; it was validated when the Mandate was created, but the builder should make sure it cannot inject CR/LF into the CONNECT request (reject with `connection_failed` or `invalid_proxy` if it does).
- UX: the user is an Agent running inside the Claude Code sandbox; nothing changes in how it calls agent-mail. When the human has not allowed the mail host, the Agent gets `proxy_refused` with the host, which it can relay so the human adds it to the sandbox's allowed domains. A misconfigured proxy variable gives `invalid_proxy` naming the variable. The operator running `mandate create` outside the sandbox sees no change unless a proxy variable is set in their shell, in which case the live login check also goes through it.
- UI: terminal output only: two new JSON error codes on stderr (`proxy_refused` with a new `host` field, `invalid_proxy`), in the existing error shape, and their `--text` rendering as for other errors. No new success output.
