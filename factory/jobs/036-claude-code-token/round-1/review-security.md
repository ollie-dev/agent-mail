## Findings
- [blocking] src/setup.rs `git_risk` (`folder.ancestors().any(|dir| dir.join(".git").symlink_metadata().is_ok())`): `Path::ancestors` is purely lexical, so the repository test walks the path as the human typed it, not the folder it names. A folder reached through a symlink (or a Windows junction) that points into a repository subfolder, e.g. `~/work/api -> /src/monorepo/services/api`, has no `.git` on any lexical ancestor. `git_risk` then returns `None` without running git, and the Agent Token is written into the repository's working tree where `.claude/settings.local.json` may well be unignored and get committed. This is exactly the leak the git-risk check exists to stop, and the spec's notes say the check must err on the side of risk. (`folder.is_dir()` follows the link, so the folder is accepted. The default from `current_dir()` is already physical; only typed paths are affected.) → Probe the resolved folder: run the `.git` ancestor walk on `std::fs::canonicalize(&folder)`, and also on the lexical path if you like. Treat a canonicalize failure as a risk (`GitFailed`), not as "outside git". Keep running git in `folder` as now. Add a Unix-only test (`#[cfg(unix)]`, `std::os::unix::fs::symlink`): `<root>/repo/.git/`, `<root>/repo/sub/`, a symlink `<root>/link -> <root>/repo/sub`; type `<root>/link` at `PROJECT_FOLDER`; script check-ignore exit 1. The test asserts the "not ignored by git" fallback, that the check-ignore command was recorded, and that no `.claude` exists under `<root>/repo/sub`.
- [follow-up] src/setup.rs `write_settings`: the temporary file `.claude/.settings.local.json.agent-mail-<pid>.tmp` holds the full token. Errors remove it, but a kill or crash between `open` and `rename` leaves it behind. Unlike `settings.local.json` itself, that name is generally not covered by the user's git excludes, so a leftover could be committed. → A later job could clean up stale `agent-mail-*.tmp` files on the next run, or name the temp file so it falls under the same ignore rule (git check-ignore it as well).
- [follow-up] src/setup.rs `git_risk`: repository detection only looks for a `.git` entry. A work tree driven by `GIT_DIR`/`GIT_WORK_TREE` or `core.worktree` from a separate git dir is missed and git is never asked. → A later job could always run `git rev-parse --is-inside-work-tree` in the folder when git is available, and treat a "yes" like a found `.git`.
