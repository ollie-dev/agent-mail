# Token setup in Claude Code, arm64 only, no audit write from the self-check tests

## Goal
Three small follow-ups (F11, F18, F19 in `factory/follow-ups.md`), all decided. An operator who reads the README's MCP server section can add the server to Claude Code without committing an Agent Token: either with `claude mcp add` in local scope, or with a project `.mcp.json` that holds only a `${AGENT_MAIL_TOKEN}` reference. `install.sh` installs the arm64 build only when `uname -m` says `arm64`. The opt-in release-binary self-check tests stop writing to the developer's real audit log.

## Context
- Stack: Rust, one binary crate. Test with `cargo test`. Lint with `cargo clippy -- -D warnings` and `cargo fmt --check`. The opt-in release-binary tests run with `cargo test --test selfcheck -- --ignored` on macOS.
- Files touched:
  - `README.md`: the `## MCP server` section (the Claude Code paragraph and the `claude mcp add` block, about lines 307-313). Also the **Release-binary tests** paragraph under the test docs (about line 438), which says "the refused `list` run adds one `denied` line to your audit log".
  - `install.sh`: the `case "$(uname -m)"` arm `arm64 | aarch64)` (line 25).
  - `tests/selfcheck.rs`: `release::ac2_unhardened_release_binary_refuses_every_keychain_access`. Its loop runs `whoami`, `list`, `mandate list` and `mandate delete deadbeef`, and it has a comment about the audit line.
  - `tests/plugin.rs`: README checks, using the existing `readme_section`, `json_blocks` and placeholder scan.
  - `tests/release.rs`: installer tests (`installer` module, `install()` runs `sh install.sh` with `PATH=/usr/bin:/bin:/usr/sbin:/sbin`), plus checks of the README and of test sources.
- Audited commands are `list`, `search`, `read`, `flag`, `move` and `draft` (README "Audit log"). `whoami` writes no audit line, and neither do `mandate list`, `mandate delete` or `--version`.

## Acceptance criteria
1. AC1: The README's `## MCP server` section offers `claude mcp add` in local scope for using Claude Code without the plugin. The section has a `sh` code block with `claude mcp add`, `--scope local`, `--env AGENT_MAIL_TOKEN=<your agent token>` and `-- agent-mail mcp`. The prose next to it says the local scope stores the entry only for you, in this project, outside the repository. Test (in `tests/plugin.rs`): `readme_section("## MCP server")` contains `claude mcp add`, `--scope local` and `AGENT_MAIL_TOKEN=<your agent token>`.
2. AC2: The same section shows a project `.mcp.json` alternative that uses Claude Code's env expansion. It is a `json` code block that parses to an object where `mcpServers["agent-mail"]` has `"command": "agent-mail"`, `"args": ["mcp"]` and `"env": {"AGENT_MAIL_TOKEN": "${AGENT_MAIL_TOKEN}"}`. The prose says the token itself then comes from the environment (for example the project's `.claude/settings.local.json` `env`, see "Agent Tokens in Claude Code and Claude Desktop"). Test: `json_blocks(&readme_section("## MCP server"))` contains a block with exactly those three values.
3. AC3: The section warns, in its own sentence, never to commit a token. The sentence names `.mcp.json` and the word "commit", for example "Never put a literal token in `.mcp.json` or any other file you commit." Test: the section contains `.mcp.json` and a sentence containing both "never" (any case) and "commit". The existing placeholder-only scan (`tests/plugin.rs`) still passes on the README, so every token value in it is `<your agent token>`, `${AGENT_MAIL_TOKEN}` or `amt_...`. The existing `ac4_readme_shows_where_agent_tokens_go` still passes, including its check that the README never contains "in the project's `.mcp.json`".
4. AC4: `install.sh` maps `uname -m` = `arm64` to `aarch64-apple-darwin` and `x86_64` to `x86_64-apple-darwin`. It no longer accepts `aarch64`. Test (in `tests/release.rs`, macOS): put a fake `uname` script first on `PATH` that prints `Darwin` for `-s` and `aarch64` for `-m`, then run the installer against the `file://` downloads directory. Expected: a non-zero exit, stderr containing `unsupported architecture aarch64`, and nothing in `~/.local/bin`. A static check also asserts that `install.sh` does not contain `aarch64)` or `| aarch64`.
5. AC5: With the same fake `uname` printing `arm64` for `-m`, the installer exits 0, and the installed `agent-mail` prints `aarch64-apple-darwin`. With `x86_64`, it prints `x86_64-apple-darwin`. This shows that narrowing the match did not break either supported architecture, whatever the host is.
6. AC6: The opt-in release-binary tests in `tests/selfcheck.rs` (`mod release`) run no audited command. The `ac2_unhardened_release_binary_refuses_every_keychain_access` loop is exactly `whoami`, `mandate list` and `mandate delete deadbeef`, each still refused with `hardened_runtime_missing`, and the comment about the `denied` audit line is removed. Test (not ignored, runs in plain `cargo test`, for example in `tests/release.rs`): read `tests/selfcheck.rs` and take the text of `mod release`. Inside it, no `run(` argument array starts with `"list"`, `"search"`, `"read"`, `"flag"`, `"move"` or `"draft"`. The array `&["mandate", "list"]` is allowed. Also, no `release` test sets `agent_mail::audit::TEST_LOG_VAR`, since none needs a redirect.
7. AC7: The README's **Release-binary tests** paragraph no longer says the tests add a line to your audit log. It says they write nothing to the audit log. Test: the README does not contain "adds one `denied` line to your audit log", and that paragraph contains "audit log" together with "nothing" or "no".
8. AC8: `cargo test`, `cargo clippy -- -D warnings` and `cargo fmt --check` pass. The in-process `ac8_refused_list_is_audited_like_store_unavailable` test is unchanged and keeps covering the refused `list` audit line against a temporary log.

## Notes for reviewers
- Security: AC1-AC3 are about where an operator puts an Agent Token. They must steer away from a literal token in any committed file. Check that every token in new README text is a placeholder (`<your agent token>` or `${AGENT_MAIL_TOKEN}`), and that the README never suggests a project or user scope that writes a literal token into a shared file. `claude mcp add` stores local scope in the user's `~/.claude.json`, keyed by project, not in the repository. The `${AGENT_MAIL_TOKEN}` form in `.mcp.json` is safe to commit because it holds only the reference. AC4 narrows what the installer accepts and changes nothing about download or checksum handling. AC6 stops a test from writing to the developer's real data directory, as CLAUDE.md requires. The tests still present only a freshly minted token that no Keychain item matches.
- UX: The operator sets up Claude Code without the plugin and reads the MCP server section. They get two options: `claude mcp add --scope local`, or a `.mcp.json` with `${AGENT_MAIL_TOKEN}` and the token in `.claude/settings.local.json`. A third note warns against committing the token. `claude mcp add` defaults to local scope, but the spec names `--scope local` explicitly so the command still works if that default changes. If an `aarch64`-reporting Mac exists at all, its operator now gets "unsupported architecture aarch64", which names the value seen and the two supported ones. A developer running the opt-in release tests no longer finds a stray `denied` line in their audit log.
- UI: The only UI surface is README text and one installer error line, which already exists and is unchanged in wording. New README paragraphs should follow the CLAUDE.md convention: at most about 300 characters per paragraph, and each thing said once.
