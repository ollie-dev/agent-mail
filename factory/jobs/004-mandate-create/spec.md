# `mandate create`: guided setup stored in the Keychain

## Goal
The human runs `agent-mail mandate create` in their own terminal. A guided prompt flow walks them through naming the Mandate, adding one or more Accounts (with the Gmail preset or generic settings), typing each Credential as hidden input, passing a live login, ticking mailboxes and operations per Account and confirming a summary. The Mandate is then sealed and stored (in the macOS Keychain in real builds), and the Agent Token is shown exactly once. After this ships, agent-mail works against a real mailbox without any hand-made fixtures.

## Context
- Stack: Rust, one binary crate `agent-mail` (ADR-0001). Test: `cargo test`. Lint: `cargo clippy -- -D warnings` and `cargo fmt --check`. Opt-in Keychain test: `cargo test -- --ignored keychain` on macOS.
- Source ticket: `.scratch/agent-mail-v1/issues/03-mandate-create.md`; feature spec `.scratch/agent-mail-v1/spec.md` ("`mandate create` guided flow", "Mandate model and sealing"); `GLOSSARY.md`; ADR-0002 and ADR-0003.
- Files this feature touches:
  - `src/mandate.rs`: the Mandate becomes `name`, short `id`, `created` (Unix seconds, UTC), `accounts: Vec<Account>` (one or more) and `policy`. Grants stay keyed by Account login.
  - `src/seal.rs`: seals and opens the new Mandate shape. The sealing guarantees stay the same: AEAD under the token-derived key, a store key derived from the token, and the token hash inside the sealed record.
  - `src/store.rs`: the Mandate store port gains `delete(key)` (the Keychain test needs it, and ticket 04 will too). It also gets a `KeychainStore` (macOS, one Keychain item per Mandate, created by agent-mail itself, service `agent-mail`, item account = the encoded store key) and becomes the `RuntimeStore` on macOS. Other OSes keep the empty store, and `put` there fails with `store_unavailable`. `InMemoryStore` stays behind `cfg(any(test, feature = "test-support"))`.
  - New Terminal port (e.g. `src/terminal.rs`). It has: an `is_interactive()` check (the real one checks that stdin and stdout are both TTYs), text input, hidden input, single choice, multi-select checklist, yes/no confirm, and message output. The real adapter uses `inquire`. A `ScriptedTerminal` behind `cfg(any(test, feature = "test-support"))` replays queued answers and records a transcript of everything shown. It records each prompt with its kind (`hidden` for Credential prompts), and it never records hidden answers.
  - New create flow (e.g. `src/create.rs`): it is driven through the core and runs the live login check through `imap::list_mailboxes`, which logs in and lists, so the same call returns the mailbox checklist.
  - `src/core.rs`: new errors for refusing to run (`interactive_terminal_required`, `sandbox_detected`), abort and store failure. Every message keeps the existing "; <next step>" rule. `list` keeps working for one-Account Mandates. For a Mandate with several Accounts it returns a structured `account_required` error naming the Account logins until ticket 13 adds `--account`. It never merges Accounts silently.
  - `src/lib.rs`: a `mandate create` subcommand with no Credential-bearing flags. `Context` carries the Terminal. There is a test-only connect override (test-support only) so that a preset host such as `imap.gmail.com` resolves to the fake server. TLS still verifies the preset host name.
  - `src/main.rs`: wires the real Terminal and the Keychain store.
  - `Cargo.toml`: adds `inquire`, plus a Keychain crate (`keyring` 4 per the feature spec, or `security-framework`) for macOS only.
  - `tests/support/mod.rs`: the fake server accepts LOGIN only with the fake Credential for a known login and answers `NO` otherwise. Its leaf certificate also names `imap.gmail.com`. Helpers for the new Mandate shape.
  - New `tests/create.rs` (scripted sessions) and `tests/keychain.rs` (opt-in). Existing `tests/list.rs` and `tests/sealing.rs` move to the new Mandate shape. Update the test-layout line in `CLAUDE.md`.
- Fake values used below: generic Account login `agent@example.test`, host `localhost`, fake server port, TLS mode implicit, Credential `fake-app-password-123`. A second Account `other@example.test` is on a second fake server. The fake server lists `INBOX`, `Archive`, `Sent`, `Spam`, `[Gmail]/Entw&APw-rfe` (shown as `[Gmail]/Entwürfe`).

## Acceptance criteria
1. AC1: A scripted session that adds a generic IMAP Account, ticks two mailboxes and the operations list and search, and confirms, results in a stored Mandate whose Policy has exactly those Grants, and prints one Agent Token. Script: name `test-mandate` → generic → host `localhost`, fake port, TLS implicit, login `agent@example.test` → hidden Credential `fake-app-password-123` → tick `INBOX`, `Archive` → tick `list`, `search` → no more Accounts → confirm. Expected: exit code 0. The `InMemoryStore` holds exactly one entry. Opening it with the printed token gives name `test-mandate`, one Account (`agent@example.test`, `localhost`, fake port, implicit) and a Policy equal to `[Grant{list, agent@example.test, [INBOX, Archive]}, Grant{search, agent@example.test, [INBOX, Archive]}]`. The transcript contains exactly one string that matches the Agent Token format (`amt_` prefix).
2. AC2: The printed token opens the stored Mandate, and `agent-mail list` with that token returns exactly the two ticked mailboxes. After AC1's session, `list` in-process with `AGENT_MAIL_TOKEN` set to the printed token and the same store returns `{"account":"agent@example.test","mailboxes":[{"name":"INBOX"},{"name":"Archive"}]}` and exit code 0.
3. AC3: Choosing the Gmail preset pre-fills Gmail's IMAP server and port, and only the address and app password are asked. Script: name → Gmail → address `agent@example.test` → hidden app password `fake-app-password-123` → tick `INBOX` → tick `list` → confirm. The test-only connect override routes `imap.gmail.com:993` to the fake server. Expected: the transcript shows no host, port or TLS prompt for that Account, only one text prompt (address) and one hidden prompt. The stored Account is host `imap.gmail.com`, port `993`, TLS implicit.
4. AC4: A wrong Credential fails the live login, shows an error and lets the human retry or abort; nothing is stored on abort. (a) Script with hidden Credential `wrong-password`: the transcript shows the login-failed error, which names the Account and not the Credential, followed by a retry-or-abort choice. Choosing retry asks the Credential again as hidden input. Typing `fake-app-password-123` then continues to the mailbox checklist, and the session completes as in AC1. (b) The same start, but choosing abort: exit code non-zero, the transcript says nothing was stored, and the `InMemoryStore` is empty.
5. AC5: A session with two Accounts produces one Mandate covering both, with separate Grants per Account. Script: Account 1 is `agent@example.test` on fake server A with `INBOX` and `list`. Answer "add another Account" yes. Account 2 is `other@example.test` on fake server B with `Archive` and `list`, `search`. Confirm. Expected: exactly one store entry. Its Mandate has both Accounts, and its Policy equals `[Grant{list, agent@example.test, [INBOX]}, Grant{list, other@example.test, [Archive]}, Grant{search, other@example.test, [Archive]}]`. No Grant names one Account with the other's mailboxes. One Agent Token is printed.
6. AC6: Declining the summary stores nothing. Script as AC1 but answer no at the summary confirm. Expected: exit code non-zero, the transcript says nothing was stored, no Agent Token-shaped string appears in the transcript, and the `InMemoryStore` is empty.
7. AC7: Run without a TTY (e.g. stdin piped), the command exits non-zero with a message saying it must be run by a human in a terminal, and stores nothing. (a) In-process with a `ScriptedTerminal` that reports non-interactive: exit code non-zero, stderr is the JSON error with code `interactive_terminal_required` and a message containing `must be run by a human in a terminal`, no prompt appears in the transcript, and the store is empty. (b) The built binary (`CARGO_BIN_EXE_agent-mail`) run as `mandate create` with stdin and stdout piped: exit code non-zero, stderr contains `must be run by a human in a terminal`. The refusal happens before any store access.
8. AC8: Run with sandbox indicators present, the command refuses with an explanatory message. With an interactive `ScriptedTerminal` and the env map containing any one of the documented indicator variables, the result is: exit code non-zero, JSON error code `sandbox_detected`, a message saying it cannot run inside an agent sandbox or session and must be run by the human in their own terminal, no prompt shown, and an empty store. Test each indicator separately. The indicators are a single named constant, at least `CLAUDECODE`, `CLAUDE_CODE_ENTRYPOINT`, `CODEX_SANDBOX`, `CODEX_SANDBOX_NETWORK_DISABLED` and `SANDBOX_RUNTIME`. The same session without them proceeds to the name prompt.
9. AC9: No command-line flag or environment variable can supply a Credential. (a) `mandate create --password x`, `--credential x` and `--app-password x` each fail argument parsing with clap's usage error and a non-zero exit, and nothing is prompted or stored. (b) `mandate create --help` lists no Credential-bearing option. (c) Run AC1's session with the env map containing `AGENT_MAIL_CREDENTIAL`, `AGENT_MAIL_PASSWORD` and `IMAP_PASSWORD` set to `env-supplied-secret`. The hidden prompt is still asked, the stored Credential equals the typed `fake-app-password-123`, and `env-supplied-secret` appears nowhere in the stored record or the transcript.
10. AC10: The Credential is never echoed and never appears in output, errors or the stored record in clear text. Across the sessions of AC1, AC4 (including `wrong-password`) and AC5: every Credential prompt is recorded as `hidden`. Neither `fake-app-password-123` nor `wrong-password` appears in the transcript, the `RunOutput` stdout or stderr, or the raw bytes of any `InMemoryStore` entry. The real adapter uses hidden input with no mask or echo.
11. AC11: The Agent Token is printed once and cannot be retrieved again by any command. After AC1's session, the token string appears exactly once in the transcript and in neither `RunOutput` stream. It is absent from the raw store key and value bytes. With `AGENT_MAIL_TOKEN` set to it, `--help`, `list`, `--text list` and `mandate create` run non-interactively print stdout and stderr that do not contain it. A second identical session prints a different token.
12. AC12: On macOS the Mandate is stored as one Keychain item created by agent-mail itself (opt-in test, ignored by default, round-trips a dummy Mandate and deletes it). `tests/keychain.rs` is `#[cfg(target_os = "macos")]` and `#[ignore]`. It seals a dummy Mandate with fake values under a fresh token, `put`s it with `KeychainStore`, `get`s back identical bytes that open to the same Mandate, then `delete`s it, after which `get` returns `None`. A plain `cargo test` reports it as ignored. The Keychain item is created by the agent-mail process, never by the `security` CLI or by any helper.

## Out of scope
- Offering a TOML export at the end of the flow, and `mandate create --from <file>` (ticket 05).
- `mandate list` and `mandate delete` commands, and listable metadata outside the sealed part (ticket 04). The store's `delete` exists here only for the Keychain test.
- `--account` selection, several tokens in `AGENT_MAIL_TOKEN`, `whoami` (ticket 13).
- The hardened-runtime self-check before Keychain access, and release signing (ticket 16).
- Audit log entries for `mandate create` (ticket 06).
- Proxy support for the live login check (ticket 14).
- Windows Credential Manager store (ticket 18).
- `*` (all mailboxes) as a checklist choice. Draft Grants get an empty mailbox list, per the feature spec, and are not exercised beyond being stored.

## Notes for reviewers
- Security: this is the first code that accepts Credentials from a human and writes to the Keychain.
  - Credentials come only from the Terminal port's hidden input. There are no flags, env variables or stdin pipes.
  - The no-TTY check (stdin and stdout) and the sandbox check run before any prompt and any store access.
  - Sandbox detection is a best-effort env-variable list. The real admin barrier is that every Credential has to be typed (ADR-0003), so review the indicator list for gaps, not for completeness.
  - The live login sends the Credential only over TLS (existing connector). Login errors must not echo the Credential.
  - The test-only connect override and the `ScriptedTerminal` must sit behind `test-support`, so no runtime env variable or flag can redirect hosts or script the terminal. Extend the existing release-marker check if practical.
  - The Agent Token goes only to the Terminal, never to stdout or stderr, so it does not land in captured agent output.
  - Server-supplied mailbox names shown in the checklist and summary should be escaped for control characters, as `--text list` already does.
  - Records from ticket 02's shape need no migration, because no real store held any.
- UX: the operator (the human mail owner) runs this in their own terminal. The flow is name → Account (Gmail preset or generic host, port, TLS mode, login) → hidden Credential → live login (retry or abort on failure) → mailbox checklist → operation checklist (list, search, read, flag, move, draft) → "add another Account?" → summary (name, Accounts with host, port and TLS, Grants; never the Credential) → confirm → seal and store → Agent Token shown once with a hint to put it in `AGENT_MAIL_TOKEN`.
  - Choosing retry re-asks only the Credential. Fixing a wrong host means abort and start again. This is acceptable for this slice, but flag it if you disagree.
  - Adding the same login twice in one Mandate should be refused with a re-prompt, because Grants are keyed by login.
  - Agents only ever see the refusal errors, which tell them to ask the human.
  - The `account_required` behaviour of `list` for multi-Account Mandates is a stopgap until ticket 13.
- UI: terminal output only. That covers the interactive prompts and checklists (`inquire`, not full-screen), the summary block, the one-time token display, and the JSON (or `--text`) refusal errors on stderr.
- Size: the ticket carries 12 criteria and changes the Mandate shape, so this branch is likely larger than a few hundred lines. The ticket's criteria were kept whole because the backlog maps one ticket to one job.
