VERDICT: CHANGES

## Findings
- [blocking] src/broker/windows.rs:~412-440 (`open_audit_log`): the log is opened with `FILE_SHARE_READ` only, for append (write access) and for read. The Broker serves each client on its own thread and every operation appends, so two concurrent appends collide: the second `CreateFileW` asks for write access that the first handle does not share, and fails with `ERROR_SHARING_VIOLATION`. The same happens for an `audit` read racing an append. Both map to `AuditUnavailable`, so a legitimate request fails closed with `audit_unavailable` only because another client was logging at that moment. Fix: open with `FILE_SHARE_READ | FILE_SHARE_WRITE` (not `FILE_SHARE_DELETE`) in both modes. Keep `FILE_APPEND_DATA` without `FILE_WRITE_DATA`, so each write stays an atomic append. Add a Windows test where several threads call `AuditLog::broker_at(..).append` at once, and one where `lines()` runs while an appender holds its handle. Both must succeed and produce the expected number of lines.
- [follow-up] src/broker/windows.rs `serve_pipe`: every accepted connection gets a thread and an unlimited pipe instance, with no read timeout. Any authenticated local user can open many idle connections and exhaust the Broker's threads and memory. A later job should bound the concurrent connections and add an idle timeout.
- [follow-up] src/broker/windows.rs `run_service`: the `match` has two arms with identical results. Merge them (cosmetic).
