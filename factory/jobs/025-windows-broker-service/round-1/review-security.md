## Findings
- [blocking] src/broker.rs:95-97 (`pipe_sddl`), used by src/broker/windows.rs:674-699 (`create_pipe`): `GRGW` for `AU` maps on a named pipe to `FILE_GENERIC_WRITE`, and that includes `FILE_APPEND_DATA` = `FILE_CREATE_PIPE_INSTANCE` (0x4). So while the Broker runs, any authenticated local user can create more server instances of `\\.\pipe\agent-mail`. `FILE_FLAG_FIRST_PIPE_INSTANCE` only stops a squatter who gets there before the Broker. Clients connect to whichever instance is listening, so a rogue instance can receive an elevated client's `create` request with the Credentials in clear, plus Agent Tokens in `run` requests. I checked this on this machine. I created a pipe with exactly this SDDL, giving full access to a foreign SID (`S-1-5-80-1-2-3-4-5`) so that the current user matches only `AU`. A second `CreateNamedPipeW` on the same name then succeeded (error 183, instance created). With `0x0012019b` for `AU` the second create was refused with error 5. The builder raises the same point in build.md. → Grant `AU` read and write without create-instance: `D:P(A;;0x12019b;;;AU)(A;;GA;;;<broker_sid>)`. Update AC2's exact string, `ac2_pipe_sddl_is_exact` and the DACL read-back test, which should check `AU`'s mask has no 0x4 bit. Add a Windows test that creates the pipe with a foreign Broker SID and checks that a second, non-first `CreateNamedPipeW` from the test process fails with access denied. The spec pins `GRGW`, so the spec has to change too. That decision belongs to the factory or the human, but the Broker must not ship with `GRGW`. Server checks on the client side (Ticket 20, `GetNamedPipeServerProcessId`) would add defence in depth but do not replace this fix.
- [fix-now] src/broker/windows.rs:442-458 (`open_audit_log`): the folder check covers reparse points and the owner, but not the folder's DACL. If `%ProgramData%\agent-mail` already exists, owned by Administrators (for example, created from an elevated process or by a future installer) and with the DACL it inherits from `%ProgramData%` (Users may create files, CREATOR OWNER gets full control), the Broker uses it. A user can then plant a regular, single-link `audit.log` that they own. That passes every file check, lets them read other users' entries and lets them forge lines with other SIDs, which the `audit` request then returns to those users. This defeats AC8's "Nothing there is user-writable". → Before each append or read, also refuse the folder unless its DACL is protected and no allow ACE for a SID other than the Broker grants any write, append, add-file, delete-child, `WRITE_DAC` or `WRITE_OWNER` right (or simply require exactly the two ACEs of `audit_dir_sddl`). The existing `path_dacl`/`ObjectSecurity::dacl` readers already do the reading. Done when: a Windows test in tests/broker.rs pre-creates `agent-mail` under the temp `%ProgramData%` stand-in with `std::fs::create_dir` (inherited, unprotected DACL), and `AuditLog::broker_at(..).append(..)` and `.lines()` both fail with `AuditUnavailable`. `cargo test --test broker` passes, and the existing AC8 tests still fail for their intended reason (the junction, link or owner) and not only because of the new check.
- [follow-up] src/broker/windows.rs:783-807 (`serve_pipe`) and src/broker.rs:346-395 (`serve_session`): every connection gets its own thread with `PIPE_UNLIMITED_INSTANCES`, no idle or read timeout, and up to 1 MiB buffered per frame. Any local user can open connections without limit, never send a byte (or send a slow 1 MiB frame), and run the service out of threads and memory. That denies the Broker to every other user. → A later job should cap concurrent connections (in total and per caller SID) and add a read deadline per frame.
- [follow-up] src/broker.rs:453-480 (`handle_create`): `create` writes no audit entry, for success or failure, so the creation of a Mandate under the caller's SID leaves no trace in the Broker's log. → Consider a metadata-only `create` audit entry with the caller's `sid` once Ticket 20 defines the operator view.
